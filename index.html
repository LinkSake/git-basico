Tu código tiene memoria

Introducción al control de versiones con Git

¿Alguna vez arruinaste un proyecto que ya funcionaba y no supiste cómo regresar a la versión anterior? ¿O trabajaste en equipo y alguien sobrescribió tu parte? Para eso existe el control de versiones. En esta experiencia vas a aprender a usar Git, la herramienta que usan equipos de desarrollo en todo el mundo para darle memoria a su código.

Al terminar podrás

Ejecutar el ciclo básico de trabajo de Git: crear un repositorio, guardar cambios, revisar el historial y trabajar con ramas. También sabrás explicar en qué parte de Git se encuentra cada cambio que haces.

1¿Por qué control de versiones?

⚡ Encuesta inicial

¿Cómo guardas hoy las versiones de tus proyectos?

El problema

Imagina una carpeta con estos archivos: proyecto.zip, proyecto_final.zip, proyecto_final_v2.zip, proyecto_final_v3_ahora_si.zip. ¿Cuál es la buena? ¿Qué cambió entre una y otra? ¿Quién hizo cada cambio? Las copias manuales no responden ninguna de esas preguntas.

La solución

Un sistema de control de versiones registra los cambios que haces a uno o varios archivos a lo largo del tiempo, de modo que puedas recuperar cualquier versión anterior cuando la necesites (Chacon y Straub, 2014). Además de regresar en el tiempo, te permite comparar versiones, saber quién modificó qué y trabajar en equipo sin pisar el trabajo de otros.

¿Por qué Git?

Git es un sistema de control de versiones distribuido: cada persona que trabaja en el proyecto tiene una copia completa de su historial, no solo de la última versión. Si el servidor central falla, cualquier copia puede servir para restaurarlo. Git nació en 2005, creado por la comunidad que desarrolla el núcleo de Linux, y hoy es el estándar de la industria (Chacon y Straub, 2014).

⚡ Verificación rápida

Un sistema de control de versiones sirve principalmente para…

El respaldo y la compresión son útiles, pero lo que define al control de versiones es el registro de cambios a lo largo del tiempo.

En Git, si el servidor donde está el proyecto deja de funcionar…

Esa es la ventaja de un sistema distribuido: cada copia es un respaldo completo.

2El modelo mental

Git toma fotografías

Otros sistemas guardan una lista de diferencias entre archivos. Git, en cambio, piensa en tu proyecto como una serie de instantáneas. Cada vez que confirmas un cambio, Git toma una "fotografía" de cómo se ven todos tus archivos en ese momento. Si un archivo no cambió, no lo vuelve a guardar: solo anota que sigue igual que en la foto anterior (Chacon y Straub, 2014). A cada fotografía la llamamos confirmación o commit, y Git le asigna un identificador único (hash) para que nunca se confunda con otra.

Los tres estados

Un archivo que Git rastrea puede estar en uno de tres estados (Chacon y Straub, 2014):

  • Modificado Cambiaste el archivo, pero todavía no le has dicho a Git que quieres guardarlo.
  • Preparado (staged) Marcaste ese cambio para incluirlo en la próxima fotografía.
  • Confirmado (committed) El cambio ya quedó guardado de forma segura en el historial.

Las tres áreas

Cada estado corresponde a un lugar dentro de tu proyecto: el directorio de trabajo, donde editas tus archivos; el área de preparación, donde eliges qué cambios entran en la siguiente fotografía; y el repositorio, donde Git guarda todas las fotografías.

Una analogía

Piensa en una sesión de fotos. El directorio de trabajo es el set, donde mueves y acomodas todo lo que quieras. El área de preparación es el encuadre: decides quién sale en la foto y quién no. El commit es apretar el botón y pegar la foto en el álbum. Una vez en el álbum, la foto ya no cambia, aunque sigas moviendo cosas en el set.

        3El ciclo básico

        Ya conoces el modelo: editas en el directorio de trabajo, preparas lo que quieres guardar y tomas la fotografía. Ahora veamos los comandos que hacen que eso ocurra.

        ComandoQué hace
        git initConvierte la carpeta actual en un repositorio. Git crea una carpeta oculta llamada .git, donde guardará todo el historial.
        git statusTe dice en qué estado están tus archivos: cuáles cambiaron, cuáles están preparados y cuáles Git todavía no rastrea. Úsalo siempre que tengas duda.
        git add <archivo>Mueve los cambios de un archivo al área de preparación. Con git add . preparas todos los cambios de la carpeta.
        git commit -m "mensaje"Toma la fotografía: guarda en el historial todo lo que está preparado, con un mensaje que describe el cambio.
        git logMuestra el historial de confirmaciones. Con git log --oneline lo ves en versión compacta, una línea por commit.

        Un buen mensaje de commit

        Tu "yo" del futuro, y tus compañeros de equipo, leerán estos mensajes para entender qué pasó en el proyecto. Escribe mensajes breves que describan el cambio con un verbo, por ejemplo "Agrega formulario de contacto" o "Corrige error en el cálculo del total" (Chacon y Straub, 2014). Mensajes como "cambios" o "ya quedó" no le dicen nada a nadie.

        En tu computadora

        La primera vez que uses Git en tu equipo tendrás que decirle quién eres, porque cada commit guarda el nombre y el correo de su autor:

        git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"

        En el simulador no hace falta (Chacon y Straub, 2014).

        Vas a empezar el sitio web de tu portafolio. Ya tienes una carpeta mi-portafolio con dos archivos: index.html y estilos.css. Ponla bajo control de versiones.

        ⚡ Verificación rápida

        ¿Qué te muestra git status?

        Para ver los commits usas git log y para ver las ramas, git branch. git status describe el estado actual de tus archivos.

        ¿Cuál es el mejor mensaje de commit?

        Un buen mensaje describe el cambio con un verbo y se entiende sin abrir el código.

        4Ramas

        ¿Para qué sirve una rama?

        Imagina que tu portafolio ya funciona y quieres agregarle una sección nueva. Si experimentas directamente sobre la versión que funciona y algo sale mal, la rompes. Las ramas resuelven eso: te permiten abrir una línea de trabajo paralela, experimentar en ella y, cuando todo esté listo, integrarla a la principal. En equipo, cada persona puede trabajar en su propia rama sin estorbar a los demás.

        ¿Qué es una rama en Git?

        Recuerda que tu historial es una serie de fotografías. Una rama es simplemente una etiqueta que apunta a la fotografía más reciente de una línea de trabajo, y que avanza sola cada vez que haces un nuevo commit (Chacon y Straub, 2014). La rama principal suele llamarse main. Git sabe en qué rama estás gracias a un indicador especial llamado HEAD.

        ComandoQué hace
        git branchLista las ramas y marca con * la rama donde estás.
        git branch <nombre>Crea una rama nueva, pero no te cambia a ella.
        git switch <nombre>Te cambia a otra rama. Tus archivos se actualizan para reflejar esa rama.
        git switch -c <nombre>Crea una rama y te cambia a ella en un solo paso.
        git merge <nombre>Integra los cambios de la rama indicada en la rama donde estás.

        Fusionar

        Cuando terminas el trabajo en una rama, regresas a main y ejecutas git merge para traer esos cambios. Si en main también hubo commits nuevos mientras trabajabas, Git crea una confirmación especial de fusión que une ambas líneas (Chacon y Straub, 2014). Si dos ramas modificaron la misma línea de un archivo, Git te pedirá que decidas cuál conservar. Eso se llama conflicto y será tu siguiente paso después de esta experiencia.

        Nota

        Si consultas Pro Git u otros materiales, verás git checkout en lugar de git switch y master en lugar de main. git switch se agregó en versiones más recientes de Git para que cambiar de rama sea más claro, y muchas plataformas usan hoy main como nombre predeterminado. El simulador acepta ambas formas.

        Cuando te cambias de rama con git switch, los archivos de tu directorio de trabajo…

        Por eso contacto.html desapareció al regresar a main en la misión: ese archivo solo existía en la otra rama.

        Quieres traer los cambios de la rama contacto a main. ¿Qué haces?

        5Un vistazo al trabajo remoto

        Hasta ahora todo ha ocurrido en tu computadora. Pero el verdadero poder de Git aparece cuando conectas tu repositorio con una copia en un servidor, llamada repositorio remoto. Esa copia sirve como respaldo, permite compartir tu proyecto y hace posible que varias personas trabajen sobre el mismo historial (Chacon y Straub, 2014).

        Piensa en el álbum de fotos de la Sección 2, pero ahora compartido en la nube. Cada integrante del equipo tiene su propio álbum completo en su computadora. Cuando alguien agrega fotos nuevas, las sube al álbum compartido, y los demás las descargan para mantener el suyo al día.

        Plataformas como GitHub alojan repositorios remotos y agregan herramientas para colaborar, como revisar cambios o dar seguimiento a tareas (Platzi, 2019). Ojo: Git y GitHub no son lo mismo. Git es la herramienta de control de versiones; GitHub es un servicio en línea que aloja repositorios de Git.

        ComandoQué hace
        git clone <url>Descarga una copia completa de un repositorio remoto, con todo su historial.
        git remote add origin <url>Conecta tu repositorio local con un repositorio remoto. origin es el nombre que se le da por convención.
        git pushEnvía tus commits locales al repositorio remoto.
        git pullTrae los commits nuevos del repositorio remoto y los integra en tu rama.

        ⚡ Verificación rápida: verdadero o falso

        git push envía tus commits locales al repositorio remoto.

        push empuja tus cambios hacia el servidor.

        Git y GitHub son lo mismo.

        Git es la herramienta; GitHub es una plataforma que aloja repositorios de Git. Existen otras, como GitLab o Bitbucket.

        git clone descarga solo la última versión del proyecto.

        Descarga el historial completo. Por eso cada copia de un repositorio Git es también un respaldo.

        ⚡ Reto final 0 de 10 respondidas

        1Llevas dos horas trabajando en app.js y guardaste todo en tu editor. Ejecutas git status y el archivo aparece como modificado. ¿Dónde está tu cambio?

        Guardar en el editor no es guardar en Git. Hasta que no ejecutes git add y git commit, el cambio solo existe en tu directorio de trabajo.

        2Quieres guardar en una sola fotografía los cambios de login.html y login.css, pero no los de notas.txt. ¿Qué haces?

        git add . prepararía también notas.txt, y un commit sin preparar no guarda nada. Preparar solo los archivos que eliges es justo para lo que existe el área de preparación.

        3Ejecutas git commit -m "Agrega formulario" y Git responde que no hay nada que confirmar, aunque sí editaste el archivo. ¿Qué faltó?

        git commit solo fotografía lo que está en el área de preparación. Si no preparaste nada, no hay nada que confirmar.

        4Clonaste el proyecto de tu equipo y quieres saber quién hizo los últimos cambios y cuándo. ¿Qué comando usas?

        git log muestra el historial con autor, fecha y mensaje de cada commit. git status solo muestra el estado actual de tus archivos.

        5Tu equipo te pide probar un nuevo diseño del menú sin afectar la versión que funciona en main. ¿Cuál es el mejor primer paso?

        Una rama te da una línea de trabajo aislada. Si el experimento no funciona, main sigue intacta. Copiar la carpeta es volver al problema de la Sección 1.

        6Terminaste el diseño en la rama nuevo-menu y ya hiciste commit. ¿Cómo lo integras a la versión principal?

        merge trae los cambios hacia la rama donde estás. Primero te cambias a main y desde ahí fusionas nuevo-menu.

        7Estás en main y no encuentras el archivo menu.css que creaste y confirmaste ayer. ¿Cuál es la explicación más probable?

        Cada rama tiene su propia versión de los archivos. Al cambiar de rama, tu directorio de trabajo se actualiza. El archivo sigue a salvo en la otra rama.

        8Ejecutaste git add estilos.css, luego cambiaste el color de fondo en ese mismo archivo y después ejecutaste git commit -m "Ajusta estilos". ¿Qué quedó guardado?

        El área de preparación guarda el archivo tal como estaba al ejecutar git add. Para incluir el cambio de color tendrías que volver a prepararlo.

        9Tu compañera subió cambios al repositorio remoto esta mañana. ¿Cómo los traes a tu copia local?

        pull trae los cambios del remoto y los integra en tu rama. push hace lo contrario, y volver a clonar es innecesario.

        10Corregiste un error por el que el total de una compra sumaba dos veces los impuestos. ¿Cuál es el mejor mensaje de commit?

        Un buen mensaje describe el cambio con un verbo y permite entenderlo sin abrir el código.

          7Cierre

          En esta experiencia aprendiste cuatro ideas que te acompañarán en toda tu carrera:

          1. Git guarda fotografías de tu proyecto, no copias sueltas de archivos.
          2. Cada cambio pasa por tres áreas: lo editas en el directorio de trabajo, lo preparas y lo confirmas en el repositorio.
          3. Las ramas te permiten experimentar y colaborar sin poner en riesgo lo que ya funciona.
          4. Un repositorio remoto convierte tu historial en algo compartido y respaldado.
